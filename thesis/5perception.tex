\chapter{Perception-Based Experiments}
\label{chap:perception}

From the previous artificially inflated inputs, we aim to move to a more realistic
example, which shows the robustness of low-dimensional controllers in a scenario involving
an image observation as input. We do this by first using our setup from the previous
chapter to scale it to a dimension, which resembles image inputs. Afterwards, we
actually build a new environment, which combines perception-based observation with
multiple actuators acting on our double integrator.

\section{Artificial Inflation to Pixel Size}
\label{sec:pixel-inflation}

\subsection{Setting}
\label{subsec:pixel-inflation-setting}

As mentioned, we take our loop from before (\cref{subsubsec:inflated-model}) and scale it up further. The input
dimension in this case becomes $18\,432$, while we set the output dimension to $256$. These numbers
were specifically selected to match the setup in \cref{sec:pixel-env}, such that we can
compare both more closely. For the input dimension, this is a $96 \times 96$ image stack of two images,
while for the output dimension it was chosen due to the specific construction.

We further note that State encoder + PPO cannot be applied at this scale, as the identification
for such large matrices is computationally impossible. Additionally, we excluded Linear PPO,
as it was only used to compare with LQR approaches before.

Due to computational complexity and time restrictions, we reduced the training steps to $10^{7}$ and
did not run experiments to determine the optimal learning rate here. Instead, we used the optimal
learning rate for \emph{large}, and scaled it up via
\begin{equation}
    \label{eq:pixel-learning-rate}
    \eta_0^{\mathrm{pixel}}
    = \eta_0^{\mathrm{large}} \sqrt{\frac{d_{\mathrm{in}}^{\mathrm{large}}}{d_{\mathrm{in}}^{\mathrm{pixel}}}}
    = \eta_0^{\mathrm{large}} \sqrt{\frac{200}{18\,432}}
    \approx 0.104\, \eta_0^{\mathrm{large}} ,
\end{equation}
rounded to two digits as in \eqref{eq:app-rl-learning-rate-grid}, which leaves us with the values in \cref{tab:pixel-learning-rates}.

\section{The New Environment and the Position-Velocity Encoder}
\label{sec:pixel-env}

\subsection{Pixelated Environment}
\label{subsec:pixelated-environment}

For our perception setup, we still use the underlying double integrator as a basis, however now
simulate its actual movement. This simulation is observed by a monochromatic camera producing $96 \times 96$-pixel
images of a mass with a radius of two pixels moving horizontally in front of a black background. The visible range
is from $-12$ to $12$ meters, so a total of $24$ meters, corresponding to $0.25$ meters per pixel. To be able to see
changes between the pictures, we hold any action commanded by the agent for $30$ time steps before
capturing another frame. The agent then receives a stack of two images as the input. \Cref{fig:pixel-setup-observation} shows
an example of such an image.

But not only the input is high-dimensional compared to the actual state. We also modify the way
our mass is actuated. We also replace the single actuator with $256$ thrusters, distributed equally around
a half circle, so thruster $i$ sits at an angle $\theta_i = \pi i / 256$. Each thruster can actuate in the
range $v_i \in [-1, 1]$, however, due to the angle, only $s\cos\theta_i$ effective acceleration is produced on
the mass, where $s$ is a scaling factor.
\footnote{We choose $s$ such that $1.5$ times the maximum acceleration demanded by our optimal controller can
be reached without clipping. Here this is $26\,\mathrm{m/s^2}$, so $s = 26/128$.}

This leads to some thrusters being more effective than others, while all are charged for the commanded output,
so some energy might be lost. For example, the only vertically acting thruster $\theta = \pi/2$ cannot
affect the mass in any way, and would thus only waste energy if used. \Cref{fig:pixel-setup-thrusters}
visualizes the thrust directions for eight thrusters.

With our chosen frame and action repeat, a pixel difference between two frames can only be guaranteed at velocities
above $0.83\,\mathrm{m/s}$. Otherwise, motion is only visible if the mass crosses a pixel boundary, making velocity
generally hard to identify. For a better approximation the number
of frames stacked could be increased, or anti-aliasing could be used to display changes better. But this will further be discussed
in \cref{sec:perception-discussion}.

\subsection{Position-Velocity Encoder}
\label{subsec:pve}

For this new environment, we introduce another feature extractor, which is based on robotic priors used
in Scalable encoder + PPO~\cite{Jonschkowski2015Learning}. Called Position-Velocity Encoders~\cite{Jonschkowski2017PVE},
it tries to encode a position and velocity state from an observation, by learning a latent position state, and then
reconstructing the velocity state using temporal differences. As we specifically look for position and velocity in our
states, we can construct even more specific priors, again in line with our reasoning that knowledge about the embodiment
helps in designing the controller architecture (\cref{sec:approach}). The priors used in~\cite[Sec.~III-B]{Jonschkowski2017PVE} are:
\begin{enumerate}
    \item Variation: ``Positions of relevant things vary.''
    \item Slowness: ``Positions change slowly.''
    \item Inertia: ``Velocities change slowly.''
    \item Conservation: ``Velocity magnitudes change slowly.''
    \item Controllability: ``Controllable things are relevant.''
\end{enumerate}

For our implementation, we follow the paper's recommended approach. Each frame is input
into a convolutional neural network (CNN), which encodes a latent position state $s^{(\mathrm{p})}_k$
from it. Its dimension is a hyperparameter, but recommended to be set to five~\cite[Sec.~III-C]{Jonschkowski2017PVE},
which we follow. The velocity is then calculated as the difference between two frames,
or $s^{(\mathrm{v})}_k = \alpha \left(s^{(\mathrm{p})}_k - s^{(\mathrm{p})}_{k-1}\right)$, where
$\alpha$ is the inverse of the time between two agent actions. For the weighting of our
prior loss terms, we use the combination suggested for similar tasks in~\cite[Tab.~I]{Jonschkowski2017PVE}, and thus
exclude the controllability prior. For the training process we further follow the one proposed in~\cite[Sec.~III-C]{Jonschkowski2017PVE}.
For details on how exactly the total loss function is constructed, we refer the reader to the original paper~\cite{Jonschkowski2017PVE}.
We train this extractor with data of $20\,000$ environment steps, which is split into $741$ episodes of $800$ environment steps,
which at our action repeat corresponds to around $27$ agent actions. Similar to before, we use $K_0$ acting on the true
state in $70\,\%$ and random actuation in $30\,\%$ of the time, before freezing the extractor's weights and using
it in front of our PPO construct (\cref{sec:ppo-variants}).

Scalable encoder + PPO is pretrained with a similar data split for this setting.

\section{Effect of Visual Inputs on the Solvers}
\label{sec:visual-inputs}

\subsection{Setting}
\label{subsec:visual-inputs-setting}

For the experiments here, we use the optimal gain under our action repeat (\cref{subsec:pixelated-environment})
as our reference and compare it with different approaches,
which here consist of Pixels + PPO (equivalent to Fully-connected PPO), Scalable encoder + PPO, Bottleneck PPO as well as our
Position-Velocity Encoder + PPO (\cref{subsec:pve}). As they reuse the already introduced architectures,
they will not be repeated here. The optimal controller for this setup actually does not
act based on the perception, but instead has access to the real state, while the output
remains our thrusters and thus gives us the actual optimal cost.
For the other approaches, except for Position-Velocity Encoder + PPO, which takes images
as an input, we flatten the images, such that they receive an $18\,432$-dimensional input vector.
The learning rates we use here are identical to the ones extrapolated in \cref{tab:pixel-learning-rates}.

However, we also modify some of our PPO parameters for this setting. Specifically, we
\begin{itemize}
    \item set $\gamma = 0.97$, which gives us around $1/(1-\gamma) \approx 33$ effective agent steps.
    Multiplying this with our agent action interval of $0.3\,\mathrm{s}$ gives us roughly $10\,\mathrm{s}$
    of effective horizon, equal to what we used before;
    \item raise the reward clipping threshold from $10$ to $\infty$, so the reward is never clipped;
    \item charge the input cost on the command before clipping, though only enact the clipped command;
    \item end the episode with a penalty if the mass exits the observable area. The penalty is set to twice the
    cost that a mass sitting at the edge of the screen would occur until the end of the episode.
\end{itemize}
The last three points relate a bit to each other, and were changes that were implemented after initial
test failures. Here, we noticed that by charging the cost only after clipping, the controller
never learned to actually control the mass in some cases. For these, it would produce increasingly larger
command inputs, but could never return from this instability, as every action above this threshold had the
same effect. Also, clipping the reward like in \cref{chap:inflation} had the side effect that leaving the
screen became an economically reasonable choice, so the model chose this behavior more often. Combined with
this, we started charging the penalty, which promotes staying on screen even more.

\section{Noisy Perception}
\label{sec:perception-noise}

\subsection{Setting}
\label{subsec:perception-noise-setting}

As our environment setup changed drastically, the cost increases associated with the noise levels
calculated from before no longer apply. Thus, we again ran a calibration with the optimal controller
to set them to respective levels (\cref{sec:app-pixel-noise-levels}). With these new values, we can use them like before
to change how the loop behaves. Parametric uncertainty still changes the underlying model, external disturbance
still acts on the position of our mass, and control noise changes the commanded actuation outputs.
Measurement noise now affects the visual input, as shown in \cref{fig:pixel-measurement-noise},
by applying Gaussian noise to all the pixels in the image. Here, we set the levels ourselves,
as the optimal controller is not acting from the camera image, but rather from the true state,
so this noise does not affect it. Still, the chosen values are found in the appendix (\cref{tab:pixel-noise-levels}).
