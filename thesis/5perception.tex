\chapter{Perception-Based Experiments}
\label{chap:perception}

From the previous artificially inflated inputs, we aim to move to a more realistic
example, which shows the robustness of low-dimensional controllers in a scenario involving
an image observation as input. We do this by first using our setup from the previous
chapter to scale it to a dimension, which resembles image inputs. Afterwards, we
actually build a new environment, which combines perception-based observation with
multiple actuators acting on our double integrator.

\section{Artificial Inflation to Pixel Size}
\label{sec:pixel-inflation}

\subsection{Setting}
\label{subsec:pixel-inflation-setting}

As mentioned, we take our loop from before (\cref{subsubsec:inflated-model}) and scale it up further. The input
dimension in this case becomes $18\,432$, while the output dimension stays at $256$. These numbers
were specifically selected to match the setup in \cref{sec:pixel-env}, such that we can
compare both more closely. For the input dimension, this is a $96 \times 96$ image stack of two images,
while for the output dimension it was chosen due to the specific construction.

We further note that State encoder + PPO cannot be applied at this scale, as the identification
for such large matrices is computationally impossible. Additionally, we excluded Linear PPO,
as it was only used to compare with LQR approaches.

\section{The New Environment and the Position-Velocity Encoder}
\label{sec:pixel-env}

\subsection{Pixelated Environment}
\label{subsec:pixelated-environment}

For our perception setup, we still use the underlying double integrator as a basis, however now
simulate its actual movement. This simulation is observed by a monochromatic camera producing $96 \times 96$-pixel
images of a mass with radius of z pixels moving along a horizontal line. To be able to see
changes between the pictures, we hold any action commanded by the agent for $30$ time steps before
capturing another frame. The agent then receives a stack of two images as the input. \Cref{fig:pixel-setup-observation} shows
an example of such an image.

But not only the input is high-dimensional compared to the actual state. We also modify the way
our mass is actuated. We also multiply the number of actuators to $256$, distributed equally around
a half circle, with their thrust direction acting on different angles on the mass. \Cref{fig:pixel-setup-thrusters}
visualizes the thrust directions for eight thrusters.

\subsection{Position-Velocity Encoder}
\label{subsec:pve}

For this new environment, we introduce another feature extractor, which is based on robotic priors used
in Scalable encoder + PPO~\cite{Jonschkowski2015Learning}. Called Position-Velocity Encoders~\cite{Jonschkowski2017PVE},
it tries to encode a position and velocity state from an observation, by learning a latent position state, and then
reconstructing the velocity state using temporal differences. As we specifically look for position and velocity in our
states, we can construct even more specific priors, again in line with our reasoning that knowledge about the embodiment
helps in designing the controller architecture (\cref{sec:approach}). The priors used in~\cite[Sec.~III-B]{Jonschkowski2017PVE} are:
\begin{enumerate}
    \item Variation: ``Positions of relevant things vary.''
    \item Slowness: ``Positions change slowly.''
    \item Inertia: ``Velocities change slowly.''
    \item Conservation: ``Velocity magnitudes change slowly.''
    \item Controllability: ``Controllable things are relevant.''
\end{enumerate}

For our implementation, we follow the paper's recommended approach. Each frame is input
into a convolutional neural network (CNN), which encodes a latent position state $s^{(\mathrm{p})}_k$
from it. The dimension of it is a hyperparameter, but recommended to be set to five~\cite[Sec.~III-C]{Jonschkowski2017PVE},
which we follow. The velocity is then calculated as the difference between two frames,
or $s^{(\mathrm{v})}_k = \alpha \left(s^{(\mathrm{p})}_k - s^{(\mathrm{p})}_{k-1}\right)$, where
$\alpha$ is the inverse of the time between two agent actions. For the weighting of our
prior loss terms, we use the combination suggested for similar tasks in~\cite[Tab.~I]{Jonschkowski2017PVE}, and thus
exclude the controllability prior. For the training process we further follow the one proposed in~\cite[Sec.~III-C]{Jonschkowski2017PVE}.
For details on how exactly the total loss function is constructed, we refer the reader to the original paper~\cite{Jonschkowski2017PVE}.
Similar to the previous chapter, we train this extractor for a total of $20\,000$ steps, here split into $1\,000$ episodes of $20$ steps,
before freezing its weights and using it in front of our PPO construct (\cref{sec:ppo-variants}).

Scalable encoder + PPO is pretrained with a similar data split for this setting.

\section{Noisy Perception}
\label{sec:perception-noise}

\subsection{Setting}
\label{subsec:perception-noise-setting}

As our environment setup changed drastically, the cost increases associated with the noise levels
calculated from before no longer apply. Thus, we again ran a calibration with the optimal controller
to set them to respective levels (\cref{sec:app-pixel-noise-levels}). With these new values, we can use them like before
to change how the loop behaves. Parametric uncertainty still changes the underlying model, external disturbance
still acts on the position of our mass, and control noise changes the commanded actuation outputs.
Measurement noise now affects the visual input, as shown in \cref{fig:pixel-measurement-noise},
by applying Gaussian noise to all the pixels in the image. Here, we set the levels ourselves,
as the optimal controller is not acting from the camera image, but rather from the true state,
so this noise does not affect it. Still, the chosen values are found in the appendix (\cref{tab:pixel-noise-levels}).
